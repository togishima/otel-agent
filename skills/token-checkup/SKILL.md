# token-checkup

otel-agent がこの PC に貯めたテレメトリから、8原則のどれが守れていないかを判定した結果を読み、本人向けに改善点を伝える。目的は本人の改善支援で、評価や比較ではない。結果はこの PC の外に出さない。

## 1. 診断結果を取る

```bash
curl -s "http://localhost:4318/api/diagnosis?days=7&top=3"
```

- 期間はユーザーが指定すれば `days` を 1 / 7 / 30 / 90 から選ぶ。指定がなければ 7。
- 接続できなければ otel-agent が動いていない。「新しいセッションを開くと SessionStart フックで起動する。テレメトリはその次のセッションから貯まる」と伝えて終える。
- `summary.sessions` が 0 なら、まだデータがないことを伝えて終える。

このスキル自体もトークンを使う。レスポンス全体を表示し直したり、追加で大量のファイルを読んだりしない。

## 2. 伝える

最初に1〜2文で全体像を伝える。

- `summary.costPerShipped`: コミットまたは PR が残ったセッション1件あたりのコスト（主指標）
- `summary.noOutputCostShare`: 変更が何も残らなかったセッションに使ったコストの割合
- `outcomes.explore` は調査や質問のセッションで、成果がないのが普通なので失敗扱いしない

次に `findings` を上から最大3件。各件について次の3点を短く書く。

1. 何が起きているか: `title` と、`examples` の日付と実測値（`value`、`detail`）。`thresholds` の対応する値と比べて、どの程度超えているか
2. なぜトークンが増えるか: 該当する原則（`principle` と `principleName`）の考え方で1文
3. 次のセッションで試すこと: `advice` を、ユーザーの状況に合わせて具体的な一言に直す

最後に「まず1つだけ試して、1週間後にもう一度見る」ことを勧める。原則8のとおり、同時に複数を変えると効果が分からなくなるため。

## 3. 具体例を見たいと言われたとき

`examples[].session` は transcript のファイル名の先頭8文字。ユーザーが望んだときだけ、その1件の最初の依頼文を見る。

```bash
f=$(ls ~/.claude/projects/*/"<session>"*.jsonl 2>/dev/null | head -1)
grep -m1 '"type":"user"' "$f" | head -c 2000
```

依頼文に、対象ファイル・症状・完了条件・検証方法のどれが欠けていたかを指摘し、書き直し例を1つ示す。transcript 全体は読まない。

## 書き方

- 責める言い方をしない。「〜できていない」より「〜すると減らせる」と書く
- 数値は丸めて、単位をつける（トークン、USD、回）
- 兆候がなければ、そう伝えて短く終える
